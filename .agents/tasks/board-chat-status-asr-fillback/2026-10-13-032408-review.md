# Chat 状态刷新与 ASR composer 回填

本次改动让非当前 Chat 的 `display` 更新触发延迟重绘，并将 ASR/Macro 从 Crew REST 草稿路径切回 Kiro Crew 的实时 composer。后续提交又补充了板端重连状态重放、Crew WebSocket 重连快照重投影，并让 K5 通过实时 composer 的 Enter 提交用户编辑后的内容。但重连重放仍会跳过没有缓存状态的槽位，板载导航编辑仍操作已经与 ASR 脱钩的 REST 草稿。FEAT-002 的验收与 findings 也仍描述旧的 K5 API 行为，不能作为当前实现的有效证据。

Watch for: **confirmed** 板端重连时缺少缓存状态的槽位不会收到任何清空帧；**confirmed** API 在线时板载删除/清空操作不会修改 ASR 所在的实时 composer；**confirmed** FEAT-002 对最终 K5 路径和测试覆盖的记录与代码不符。

**Verdict**: NEEDS_CHANGES

## High-level view

固件现在会立即重绘当前槽位，并为非当前槽位设置 `s_lcd_redraw_pending`，因此三个侧栏颜色可随任意 `display` 帧更新。Companion 在板连接时从 `kc_status` 重放缓存投影，但 `filter_map` 会完全跳过未绑定、刚换绑或尚无缓存的槽位；固件在 `hello` 时又不清理会话状态，因此这些槽位可继续显示上一次连接留下的颜色。

ASR 和 Macro 现在落入既有 `Compose` 路径，只聚焦窗口并输入文本，不注入 Enter。K5 也回落到同一控制器并注入 Enter，能够提交用户在真实 composer 中修改后的内容；但 API 路由仍截获左键删除、长按删词和上键长按清空，将它们应用到 `crew_api_drafts`，因此板载编辑操作与屏幕上可见文本分离。

Crew WebSocket 每次连接成功都会清空槽位去重缓存，使首个完整 `slots` 帧重新进入 `apply_status`。这解决了相同快照在 WebSocket 重连后被抑制的问题，但当前 FEAT-002 findings 仍声称 K5 继续走 API submit，并将只有底层 Compose 映射的既有测试表述为 API 回落路由已被单测验证。

## 板端重连只重放命中缓存的绑定

`connect_device` 在 `companion/src-tauri/src/lib.rs:715-733` 遍历前三个绑定，但通过 `inner.kc_status.get(...)?` 的 `filter_map` 只生成命中缓存的帧。固件的 `hello` 分支只更新连接状态并回复 `hello_ack`，不会清空 `s_sessions`，所以 Companion 重连并不等于显示历史为空。**confirmed**：如果某个槽位在断线期间被解绑、换绑到尚无状态的新会话，或者缓存中没有该会话，该槽位不会收到帧并继续显示旧状态。重放应覆盖固定的三个槽位，缓存缺失时显式发送 `state="unbound"` 和空文本。

Crew WebSocket 侧在连接成功时清空 `crew_api_slots`，首个 `slots` 快照会重新进入 `apply_status`。这只能更新快照中有状态且满足绑定/Watch 条件的槽位，不能替代板连接时对三个槽位的完整初始化。

## 实时 composer 与板载编辑路径分叉

`route_board_via_crew_api` 在 `companion/src-tauri/src/lib.rs:1604-1607` 让 ASR、Macro 和 K5 回落到 `ControlRouter`。ASR/Macro 生成 `ControlAction::Compose`，K5 Down 生成 Enter，因此填入与提交都针对用户可见的实时 composer。

同一个 API 路由在 `lib.rs:1608-1618` 仍消费 `NavDir::Left` 的短按删除和长按删词，以及 `NavDir::Up` 的长按清空，并调用 `edit_crew_draft` 修改 `crew_api_drafts`。ASR 已不再写这个 store，K5 也不再提交它。**confirmed**：API 在线且存在 active slot 时，这些操作返回 `true`，后续实时 composer 控制器不会收到事件，用户看到的 ASR 文本不会变化。应让这些编辑事件与 ASR/K5 一样回落，保持输入、编辑和提交使用同一个 composer。

## FEAT-002 对 K5 和验证范围的记录已经过期

最终代码删除了 `submit_or_continue_crew_slot`，并让全部 K5 帧回落到旧控制器；只有 Down/Long 会由 `route_input` 映射为 Enter。FEAT-002 的 acceptance criteria 和 findings 仍写着 “K5 submit/continue via the Crew API are unchanged”，与最终代码相反。**confirmed**：该记录不能支持当前行为，应更新为 K5 在实时 composer 注入 Enter，以保留用户编辑结果。

`cargo test` 的 97 个测试全部通过，其中 `asr_text_routes_to_compose` 只验证 `kirocrew_control::route_input` 的底层映射；它没有经过 `route_board_via_crew_api`，也没有验证 API 在线时 ASR 不被消费。FEAT-002 findings 称“routing behavior is covered”超出了现有证据。应在既有测试模块补充该决策的覆盖，或准确记录人工代码审查范围和硬件端到端限制。
